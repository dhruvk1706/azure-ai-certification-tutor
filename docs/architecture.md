# Architecture

```
Browser ──► frontend (Vite, React) ──► backend (FastAPI) ──► db (PostgreSQL + pgvector)
                                              │
                                              └──► LLM endpoint (hosted provider or Ollama)
```

## Components

- **frontend:** a single-page app. It talks only to the backend, so LLM keys never reach the browser. Pages use Tailwind palette classes directly, and `src/index.css` themes them by redefining the palette: an azure blue ramp, and in dark mode every scale mirrored, selected by `data-theme` on `<html>` (set before first paint by `index.html`, then by the header's Theme menu). A render error in one page shows a recoverable message, not a blank app.
- **backend:** the only component that touches the database or the LLM.
- **db:** one PostgreSQL instance holds both relational data and embeddings. pgvector removes the need for a separate vector store. The extension is enabled on first start by `infrastructure/postgres/init/`.
- **LLM endpoint:** chosen by configuration, not code. The backend uses the `openai` SDK as a generic client for any OpenAI-compatible API. Switching provider means changing `.env` (see the README). Ollama runs only under the `ollama` Compose profile.

## LLM integration rules

Implemented in `backend/app/learning/llm.py`, the only module that calls the model:

- **No provider defaults or branches:** read the endpoint, key and model from configuration and fail with a clear error if they are missing. Never branch on provider name.
- **Pass the endpoint and key explicitly:** left unset, the SDK falls back to OpenAI's URL and the `OPENAI_*` environment variables, which would silently send data to the wrong service.
- **Use the common API subset:** chat completions and embeddings are the most widely supported endpoints. Don't depend on anything only one provider offers.
- **Don't assume an embedding size:** it varies by model, and a pgvector column has a fixed dimension. Changing embedding model means re-embedding existing content.

## Syllabus ingestion

`backend/app/syllabus/` turns the official study guide into versioned rows. It runs as a command and knows nothing about embeddings, RAG or quizzes. The API reads its tables but never runs ingestion or writes to them.

- **Flow:** fetch, parse and validate, then write in one transaction. The database is not opened until the page has passed validation, so a bad fetch or a redesigned page changes nothing. A response shorter than its `Content-Length` is rejected before parsing. The parser separately requires proof the page ended normally (`</main>`, and a heading after the syllabus section), because a connection that drops without a `Content-Length` looks like a normal end. Completeness is judged from page structure, never from item counts, so the syllabus can legitimately grow or shrink.
- **Fail closed:** the parser rejects anything unexpected, including a wrong language or exam, a domain count other than five, a mismatch with the "Skills at a glance" list, and unknown headings. Inside the skills section, any text outside a heading or bullet is an error, as is any element other than the known structural and inline tags, so content can't vanish without notice. The section's order is fixed (audience, at-a-glance, then domains) and it may end only at the "Study resources" heading. What follows is validated too, because that heading could appear too early: one intro paragraph and tables but no bullets or bare text, then optionally an "Additional resources" section holding only page chrome and a "Last updated" date bullet. The page must have exactly one `<main>`, and elements inside it must nest correctly, allowing for void elements and end tags HTML makes optional. Outside it, headings, bullets and paragraphs are accepted only where the live page has site chrome: the outline heading in `<aside>`, the footer link list and theme menu, and the browser notice. Bare text outside it must be document metadata or a link or button in the header or footer. The HTML parser never reports the content of comments, declarations and tags as text, so inside a heading or bullet any of these is an error, and in the skills section so is any comment holding markup or a tag with markup in its attributes. Moved boundaries, crossed elements and hidden tokens therefore can't strand objectives or their tails. A legitimate restructure therefore needs a parser change, on purpose.
- **Change detection:** the content hash covers the parsed syllabus only (normalized text, weights, effective date and order), so markup and page chrome cannot affect it. A new hash adds a new version plus its differences from the previous one in `syllabus_change`. Earlier versions are never rewritten.

## Learning

`backend/app/learning/` holds the tutor, lessons, learning path and progress. Migration `0002` only adds tables.

- **Identity:** the project has no accounts, so `POST /api/learners` creates an anonymous learner and returns a random bearer token once. Only its SHA-256 is stored. Every query on learner data filters on the authenticated learner, and another learner's row answers 404.
- **Retrieval:** the syllabus is the only source text, about 64 short objectives, so search is deterministic lexical ranking over those rows (`retrieval.py`). It needs no embedding model, and it means a question sharing no word with the syllabus finds nothing. pgvector stays available if that proves too weak.
- **Grounding:** references are snapshots of real syllabus rows chosen by the server, never by the model. Only a question that matches the syllabus, or one that refers back to earlier context ("simplify that", "Why?"), gets references. A follow-up keeps the previous answer's references, or else takes the learner's chosen topic, so a chosen topic never attaches itself to an unrelated question. Each reference is labelled with why it is there. With none, the answer is marked as having no source. Sources are numbered by the server, so citation numbers outside that range and all URLs are removed from model text. This stops invented citations, but it can't verify the model's own Azure claims, so the UI labels them as AI-generated.
- **Untrusted text:** retrieved text and the learner's question are escaped and wrapped in tags the system prompt declares to be data. History is capped at 12 messages of 2000 characters, and requests have length limits.
- **Failure:** the model is called with no transaction open and before any write, and each exchange is stored in one transaction. A failed call therefore stores nothing, and the same `client_message_id` makes a retried send safe.
- **Lessons:** one row per syllabus version, topic and depth, shared between learners because the prompt contains only syllabus text. The model's reply must validate against a schema, with one retry. Answers stay on the server until the learner submits, and the server grades them.
- **Learning path:** `learning_plan` stores inputs only. `plan.py` recalculates the order and schedule from those and stored progress on every read, so adjusting a plan can't lose completion records. Objectives are ordered by domain weight (to the nearest 10%, which keeps close domains in syllabus order) times how weak the learner is on them, with a failed comprehension check counting as weakest, kept together by skill, and ties in syllabus order. The model only narrates the result, on request.
- **Versions:** `topic_progress`, `learning_plan`, `lesson` and `conversation` each point at one syllabus version. A learner's active version is the newest they have a plan on, otherwise the newest they have progress on, otherwise the latest ingested, so ingestion never moves a learner who has started.
- **Requests:** the API stays synchronous and non-streaming. Long model calls hold a worker thread but not a database connection.

## Practice and mock exams

`backend/app/assessment/` holds the question bank, Microsoft Learn sources, practice quizzes, mock exams and analytics. Migrations `0003` and `0004` only add tables.

- **Sources:** `python -m app.assessment.sources add --subskill ID <url>` fetches a `https://learn.microsoft.com` page (no other host), keeps the text of its article blocks, and attaches it to objectives. Like ingestion it validates before opening the database and writes in one transaction. A page's text is never rewritten: changed text is a new `learn_source` row, and generation uses the newest text of each page. Objectives belong to one syllabus version, so a source attached to a version 1 objective verifies nothing on version 2. The API never fetches pages.
- **Generation:** the model gets the objective and the Learn text, both as data, and must return each question with the exact sentence from the source that proves its answer. A question is stored only if it validates against a schema (four distinct options, one answer); has no "all of the above"-style option, link or claim to be a real exam item; its excerpt appears verbatim in the cited source and contains a term of the correct option that no distractor has (a word every option shares proves nothing); it isn't the same as, or nearly the same as (80% term overlap), a stored question; a second model call, shown only the excerpt and options, picks the same single answer and calls it supported and unambiguous; and a third, shown the excerpt, answer and explanation, finds every claim in the explanation in the excerpt. An unreadable verdict fails the request. The model calls are judgments, so they reduce wrong questions rather than rule them out. At most the three newest attached pages go into a prompt.
- **Cost limits:** learner tokens are free to create, so generation is limited from a `question_generation` log (migration `0004`): each request is committed before the model is called, then counted, so failed calls count, refused ones don't, and a race can only undershoot a limit. Defaults are 10 requests per learner and 60 overall per hour (`QUESTION_GENERATION_LEARNER_HOURLY_LIMIT`, `QUESTION_GENERATION_HOURLY_LIMIT`; 0 turns generation off), answered with 429. An objective stops taking questions at 40. The tutor, lesson generation, plan narration and lab assistant share a separate limit (`llm.reserve`): 60 requests per learner and 300 overall per hour by default (`LLM_LEARNER_HOURLY_LIMIT`, `LLM_HOURLY_LIMIT`; 0 turns them off), answered with 429 before the model is called. It is counted in memory, so it resets when the backend restarts and assumes a single worker process. Opening a stored lesson doesn't count, because lessons are cached per topic and depth. The objective, version, difficulty and format are set by the server. Model calls happen before any write, accepted questions are inserted together, and a unique fingerprint per version stops concurrent duplicates, so a failed or partial generation can't corrupt the bank. Questions are never edited, only retired.
- **Grading:** the browser sends an option index, never a score or verdict. Correct answers and explanations leave the server only after that answer has been graded: at once in practice, where an answer is then final, and at submission for a mock exam. Every attempt write locks the attempt row and changes state with conditional updates (submit only from `in_progress`, change an answer only while it is ungraded), so concurrent or repeated submissions grade once and return the same result. Starting is idempotent on `client_attempt_id`.
- **Timers:** a mock exam stores its deadline in server time. Writes after it are refused, and the next request that touches an overdue exam (opening it, the history, analytics) submits it as of its deadline with the saved answers. Nothing depends on a process staying up, so restarts lose nothing. The browser countdown is only a display.
- **Selection:** mock exams spread questions over domains by exam weight (Sainte-Laguë, passing a short domain's share on), pick unseen questions first, and refuse to start with fewer questions than asked for. Adaptive practice orders questions answered wrong last time first, then unseen ones, then ones answered right, and within each puts objectives with the weakest record (smoothed) in the heaviest domains first.
- **Analytics:** recomputed on every read from graded answers on the learner's version. Unanswered practice questions don't count; unanswered mock questions count as wrong. Readiness is accuracy per domain weighted by exam weight, with untried domains at 0%, and gives no verdict below 20 answers or 3 in any domain. The 70% mark is a practice threshold, not Microsoft's scaled score.
- **Versions:** questions and attempts each point at one syllabus version. A practice attempt pins the learner's active version, like a plan or progress.

## Azure sandbox and guided labs

`backend/app/sandbox/` simulates a small part of Azure so learners can practise AI-103 tasks with no subscription. Nothing calls Azure, and no credentials are asked for or stored. Migration `0005` only adds tables.

- **Resources:** every simulated resource is one `sandbox_resource` row: type, name, parent, validated `properties` (configuration) and `outputs` (what the simulation computed, such as test results). `catalog.py` defines each type's fields, naming rule and rules from its Microsoft Learn page, with a `note` where it simplifies. It plays the part of Azure Resource Manager: what Azure would refuse on save (bad names, limits, quota, missing references, changing a setting fixed at creation, editing existing index fields) is refused with 422 or 409. Mistakes Azure would accept, such as a region that breaks a scenario, are saved and graded by labs.
- **Engine:** `engine.py` creates, updates, deletes and runs actions. Every write locks the learner's `sandbox` row with a no-op `UPDATE` (a write lock on PostgreSQL and SQLite alike), loads all their resources, and commits once, so checks that span resources can't be raced and a rejected operation changes nothing. Updates must send the `version` they read. Creates are idempotent on `client_request_id`. Names are unique per learner in the scope Azure uses, by a unique constraint; AI service accounts share one namespace.
- **Lifecycle:** deleting a resource deletes its children. Foundry and Document Intelligence resources are soft-deleted instead, keep their name for 48 hours, and can be recovered (into a resource group of the same name) or purged; after 48 hours the next write purges them. A content filter in use can't be deleted. Web apps start and stop.
- **Simulation:** `simulate.py` answers run-time questions by rules over stored rows: prompt tests against content filter thresholds, agent tests that walk connection, authentication, index, vector and semantic checks and then retrieve from a built-in five-document corpus, app connection tests over network, identity and roles, and precomputed Document Intelligence results. No model is called, and results say so.
- **Labs:** `labs.py` holds seven labs. Each check is a function over the lab's own resource group that returns `None` or feedback saying what is wrong and why, without the full answer. Grading (`POST /validate`) runs every check on stored state under the sandbox lock and stores the result as history, idempotent on `client_validation_id`. Starting a lab creates its starter resources through the same validated engine. Reset deletes only that lab's resource group (and purges what it soft-deleted), then recreates the starter resources; completion records, history and hints are kept. Lab progress lives in its own tables, so Phase 3 and 4 progress and analytics are untouched.
- **Syllabus mapping:** labs name objectives by their text in the live study guide. They are matched to the learner's active version by exact text, else by the tutor's lexical search, so references are always real rows; with no syllabus ingested, labs still work and show the text.
- **Assistant:** `POST /labs/{id}/assistant` uses `llm.complete`, with no transaction open and nothing stored. Its prompt holds only what the learner can see: the lab text, their resources, the latest validation feedback and the hints they revealed. Check code and unrevealed hints never enter it. All of it is escaped and wrapped in tags the system prompt declares to be data. Links are removed from replies, and the reply is shown as AI-generated next to, never instead of, the server's grade.

## Decisions

- **Migrations:** Alembic, configured in `backend/pyproject.toml`, with migrations in `backend/app/migrations/`. `infrastructure/postgres/init/` only runs when a database volume is first created, so it stays limited to enabling extensions. Migrations are applied by command, not at startup.

- **Monorepo layout:** npm workspaces at the root for JavaScript, uv in `backend/` for Python.
- **Top-level `tests/`:** tests sit outside the packages they cover. `tests/frontend` resolves packages from the root `node_modules`, which is why the root is an npm workspace.
- **Docker Compose is for local development only:** it runs dev servers with source bind-mounted, and publishes ports on `127.0.0.1` only. It is not a production setup.
- **Configuration:** one root `.env`, based on `.env.example`, is shared by Compose, the backend and Vite. Vite only exposes `VITE_*` values to the browser.
